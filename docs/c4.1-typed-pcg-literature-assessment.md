# C4.1 typed-PCG literature assessment

**Status:** literature screen, 2026-08-28. This is not an implemented C4.1.

**Superseded budget notice (2026-08-29):** this historical screen used the
old `18,273,600-B` setup-increment ceiling. The owner subsequently allowed
total setup up to `3x` measured C4, giving a `76,742,930-B` increment. Current
construction, setup, security, and timing estimates are in
[`c4.1-folded-query-high-degree-typed-ole.md`](c4.1-folded-query-high-degree-typed-ole.md);
do not use the rejection conclusions below under the relaxed budget.

## Target and hard budget

The desired rate-1/4 C4.1 response is

```text
C4 anchor response                         84,544,352 B
Packed16 response saving                  -18,273,600 B
C4.1 target response                       66,270,752 B

measured C4 setup                          38,371,465 B
maximum C4.1 setup                         56,645,065 B
maximum typed-PCG increment                18,273,600 B
typed objects                              15,552,000
complete setup budget per object                 9.4 bits
```

For every object the required dealerless two-party functionality is, under one
verifier-held external `Delta in Fp2`,

```text
u <- uniform {0,...,2^16-1}
b <- uniform {0,1}
k_u = m_u + Delta * u   in Fp2
k_b = m_b + Delta * b   in Fp2
```

The prover receives `(u,b,m_u,m_b)` and the verifier receives
`(Delta,k_u,k_b)`. The complete malicious setup, including both directions,
base correlations, seed/key material, checks and framing, must fit in
`18,273,600 B`.

## Most relevant constructions

### Li--Xing--Yao--Yuan: PCGs for any finite field (EUROCRYPT 2025)

Local AnyDoc conversion:
[`2025-169-efficient-pcg-any-finite-field.md`](2025-169-efficient-pcg-any-finite-field.md).
Primary source: <https://eprint.iacr.org/2025/169>.

This is the closest basis on the `Fp2` side. It gives programmable OLE over any
finite field and authenticated multiplication triples, including authenticated
Boolean triples, with malicious distributed seed generation.

It is not an off-the-shelf typed-PCG for C4.1:

- the authenticated values and MACs are constructed in compatible finite-field
  domains, not as bounded `u16` values under an externally fixed odd-prime
  `Fp2 Delta`;
- ordinary OLE expansion gives field-uniform values; truncating them to 16 bits
  does not preserve the MAC equation or the required distribution;
- the paper's malicious `Input(P,x)` communicates `log(q)` bits per party for
  each supplied `x in Fq`, so feeding all typed values through the generic input
  interface is necessarily linear and misses the C4.1 gate;
- the paper reports `47.54 MB` per-party point-to-point communication for one
  concrete batch of `3^16` authenticated Boolean triples with 128-bit MACs,
  already above the entire `18.2736 MB` typed increment before producing the
  C4.1 object or its `Fp2` bridge.

That `47.54 MB` measurement rules out reuse of the paper's authenticated-triple
generator; it does **not** prove that every specialization of its simpler
programmable OLE core must exceed the gate. The paper gives no secure parameter
set or concrete byte count for VOLTA's fixed-`Delta`, bounded-input relation, so
such a specialization remains an unquantified research candidate.

Its asymptotic `O(k log N)` OLE communication means a *new direct relation-PCG*
may still be plausible: program the expansion to emit the two C4.1 MAC
equations directly, rather than generate bits and lift each output afterward.
The cited paper does not provide that construction or a concrete serializer
below the gate.

### Li--Xing--Yao--Yuan: PCGs over `Z/p^k Z` (CRYPTO 2025)

Local AnyDoc conversion:
[`2025-1223-efficient-pcg-over-z-pk.md`](2025-1223-efficient-pcg-over-z-pk.md).
Primary source: <https://eprint.iacr.org/2025/1223>.

This is the closest basis on the `u16` side. It gives OLE over Galois rings and
two-party `SPDZ_2^k`-type authenticated multiplication triples. With `k=16`,
the value domain naturally has the desired 16-bit support.

It still does not provide the C4.1 correlation:

- its global MAC key and authenticated values live in a characteristic-two
  ring, whereas VOLTA requires the existing verifier-held `Delta in Fp2` over
  an odd-prime field;
- there is no ring homomorphism that embeds `Z/2^16 Z` into that `Fp2`, so the
  ring MAC cannot simply be reinterpreted as a VOLTA MAC;
- a cross-domain equality/conversion proof is still necessary.

The paper's per-party seed upper bound for an authenticated batch is

```text
(m*c^2*t^2 + c*t) * (log2(N)-log2(t)+1) * (lambda+2)
  + lower-order terms bits.
```

Using the paper's attack-resistant 128-bit family `m=2,c=5,t=27` and
`N=15,552,000` gives approximately `95,766,568 bits = 11,970,821 B` for
**one party's seed**. Even the optimistic one-seed count leaves only about
`6.30 MB` for the other party, distributed generation, malicious checks and
the indispensable `Fp2` bridge. Counting two similarly sized seeds is about
`23.94 MB` before that bridge, already outside the gate.

Consequently this construction is useful as a design reference, but the stated
instantiation cannot be composed with a conversion protocol and meet C4.1.
The concrete QA-SD parameter sets also need independent review: the paper itself
revises parameters in response to newer folding/decoding attacks and labels an
older benchmark family as broken. A C4.1 design must use the revised families,
not recover bytes by returning to the obsolete parameters.

### Agarwal--Baum--Braun--Scholl: low-bandwidth mixed arithmetic

Primary publication: <https://doi.org/10.1007/978-3-031-91134-7_14>.
Reference implementation: <https://github.com/AarhusCrypto/vole-zk-conversions>.

This work is relevant because it replaces older cut-and-choose arithmetic /
Boolean conversions with low-degree PRGs and polynomial constraints. It is the
best reference found for a *batched bridge* between domains.

It does not itself generate the C4.1 setup object. Its protocols operate inside
a VOLE-based ZK proof system and verify mixed-domain conversions; they do not
give a dealerless malicious PCG that silently distributes the exact asymmetric
`(u16, bit, Fp2-MAC)` correlation under VOLTA's external `Delta`, nor a concrete
15,552,000-object setup below `18.2736 MB`.

The publisher endpoint returned an HTML access page instead of the article PDF,
so no fake `.pdf` or incomplete AnyDoc conversion is retained here.

## Conclusion

No compact existing typed-PCG found in this screen can be adapted by a local
wrapper while preserving the current C4 security interface and meeting the
exact byte target.

The only credible research path is a hybrid of the first and third ideas:

1. use a programmable PCG to emit the `Fp2` MAC shares directly under the
   verifier's external `Delta`;
2. derive `u16` and the carry bit from a low-degree PRG inside that same
   expansion;
3. use one batch polynomial check for range/bitness and correspondence, with no
   per-value lift or correction word;
4. serialize and count the complete two-party malicious setup; reject the
   design unless the increment is at most `18,273,600 B`.

This is a new mixed-domain programmable correlation generator, not a parameter
choice of either cited PCG. The asymptotics do not rule it out, but the current
literature does not establish its concrete feasibility. Until a construction,
proof and byte-accurate serializer exist, `66,270,752 B` remains a conditional
response projection rather than an achievable C4.1 result.

## Screened but not retained as primary candidates

- FOLEAGE and Ferret efficiently generate characteristic-two correlations, but
  the per-bit `Fp2` lift is the fatal cost.
- BarnOwl changes the trust model to three parties with honest majority.
- Dory reduces streaming PCG memory, not the mixed-domain functionality.
- Secret-replication PCFs cover linear and small-domain VOLE-style
  correlations, but do not provide the bounded cross-characteristic object
  under the existing external `Delta`.
