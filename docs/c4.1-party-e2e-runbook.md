# C4.1 party-separated A100-to-Debian runbook

Status: local runbook only. It does not authorize pod contact. The active
authority and hard stop remain in `prototype-status.md`.

## Artifacts and trust boundary

One clean Debian setup creates, with `create_new` semantics:

- `provider.bundle`: prover correlations and typed prover seeds/tags; secret,
  one response only;
- `verifier.bundle`: verifier-only `Delta`, ordinary VOLE keys, typed seed
  keys and compact verifier model; secret, never leaves Debian;
- `model-setup.bin`: locally pinned model/quantization/PCS identities and the
  two deterministic PCS roots; public; and
- `manifest.json`: exact byte lengths, BLAKE3 digests, setup/model-init timing,
  setup traffic, security values and clean Git SHA.

The incremental typed verifier state is exactly `4,145,152 B`. The verifier
bundle also contains the ordinary VOLE keys already required by the C4
protocol; its full size is reported separately and must not be described as
typed-slab storage.

The pod receives only `provider.bundle`. `p6_report` validates its expected
length and BLAKE3, decodes it canonically, deletes and fsyncs the consumed
file after the mock fail-closed schedule prepass and before production
proving, and refuses warmups or multiple responses. Its PCS roots must
reproduce the BLAKE3-pinned local `model-setup.bin`.

## Preconditions

Do not execute the remaining sections until the ledger records a new owner
GO and names an authenticated HTTPS artifact service. Use independent,
single-use pre-signed PUT/GET URLs with short expiry. Do not put URLs or
bearer tokens in Git, shell history, process arguments, logs or result JSON.
Expected byte lengths and BLAKE3 digests travel over the authenticated control
channel and are checked again by both binaries.

Both machines must have at least 60 GiB free before a broad build. The pod is
one A100-SXM4-80GB with `CUDA_VISIBLE_DEVICES=0` and eight Rayon workers. The
Debian verifier uses one or four workers, no CUDA, a 2-GB RSS hard stop and a
target below 512 MB.

## 1. Pin source through GitHub HTTPS

On Debian, checkpoint and push `main`. Record the full SHA. On the pod, the
remote must be `https://github.com/...`; use `git fetch`/`git pull` over HTTPS,
then require the same full SHA and a clean tree. Git-over-SSH, `gh`, SCP,
rsync, repository archives and exported credentials are forbidden.

## 2. Create one setup on Debian

From the clean pinned SHA:

```bash
source ~/.cargo/env
cd rust
cargo build --release -p volta-bench --bin c41_party_setup --bin c41_verify_client
target/release/c41_party_setup \
  --weights ../benchmarks/weights \
  --output /absolute/fresh/c41-setup \
  --authorization-store /absolute/durable/c41-setup-authorizations \
  --response-index 0
```

Keep the setup directory mode `0700`; secret files are `0600`. Check the
manifest is clean, real/AES, above 78 bits for both security fields, and has
the frozen production census. Upload only `provider.bundle` with its
single-use HTTPS URL. After a successful authenticated upload, delete the
local provider copy; retain `verifier.bundle`, `model-setup.bin`, the setup
manifest and durable authorization state.

## 3. Produce once on A100

Build the CUDA backend and the unchanged release producer once:

```bash
source ~/.cargo/env
cd rust
NVCC=/usr/local/cuda/bin/nvcc VOLTA_CUDA_ARCH=sm_80 ../scripts/build_cuda_backend.sh
VOLTA_CUDA_LIBRARY=../target/cuda/libvolta_cuda_backend.so \
  cargo build --release --features cuda -p volta-bench --bin p6_report

CUDA_VISIBLE_DEVICES=0 RAYON_NUM_THREADS=8 VOLTA_REQUIRE_CUDA=1 \
VOLTA_CUDA_LIBRARY=../target/cuda/libvolta_cuda_backend.so \
target/release/p6_report \
  --c4-record --c4-profile anchor --c41-e2e-record \
  --accelerator cuda-resident --resident-timing wall-only-counters \
  --pcg-backend real --ggm-prg aes128-mmo \
  --warmup-repetitions 0 --repetitions 1 \
  --c41-provider-bundle /absolute/incoming/provider.bundle \
  --c41-provider-bundle-bytes PROVIDER_BYTES \
  --c41-provider-bundle-blake3 PROVIDER_BLAKE3 \
  --c41-model-setup-blake3 MODEL_SETUP_BLAKE3 \
  --c41-artifact-output /absolute/fresh/c41-public
```

Run to completion even if the prover ratio exceeds `1.30x`. Do not retry with
the consumed bundle. Upload via new single-use HTTPS URLs the proof,
statement, public manifest and new A100 JSON. `model-setup.bin` from the pod
is diagnostic equality evidence; the verifier uses the locally initialized
copy. Record transfer time separately from prover and verifier time.

## 4. Verify on Debian

Download to fresh paths, check all lengths/BLAKE3 values, and compare the pod
manifest Git SHA, model-setup digest, C41FS1 context digest and exact challenge
count. Then run the first committing verification:

```bash
source ~/.cargo/env
cd rust
target/release/c41_verify_client \
  --verifier-bundle /absolute/fresh/c41-setup/verifier.bundle \
  --model-setup /absolute/fresh/c41-setup/model-setup.bin \
  --expected-model-setup-blake3 MODEL_SETUP_BLAKE3 \
  --statement /absolute/fresh/c41-public/statement.bin \
  --proof /absolute/fresh/c41-public/proof.bin \
  --expected-proof-bytes PROOF_BYTES \
  --expected-proof-blake3 PROOF_BLAKE3 \
  --expected-git-sha FULL_GIT_SHA \
  --expected-fs-challenges FS_CHALLENGES \
  --expected-fs-context-digest FS_CONTEXT_BLAKE3 \
  --authorization-store /absolute/durable/c41-verifier-authorizations \
  --threads 4 \
  --output /absolute/fresh/c41-verifier-4t.json
```

The index is durably burned before proof read/decode. Acceptance requires a
proof below `70,000,000 B`, zero materialized typed lot/query, exact
correlation and C41FS1 census, both PCS checks, product/zero close, one
degree-12 close and RSS below 2 GB. Verifier time starts at proof read and
ends at verdict; inventory/model initialization and network transfer are
separate. A one-thread rerun may use `--benchmark-replay` only, is diagnostic,
and cannot claim a second response.

## 5. Records and cleanup

Copy the A100 and Debian JSONs into new `benchmarks/results/` names, update the
ledger, commit and push through GitHub HTTPS. Never commit proof, setup or
secret bundles. Remove the canonical `rust/target` and pod/local transient
artifacts after the checkpoint; retain only the durable burn records required
to prevent index rollback/reuse. Stop the pod and verify termination.

## Prover diagnostics

The A100 JSON separates lot expansion and D2H preparation; matrix
registration; bridge construction and sparse-entry count; dense-query build,
final bytes and Rayon scratch upper bound; query/bitmap H2D; fused-fold
submission; fold D2H/synchronization; degree-12 close; cleanup; model codec;
each PCS commit/open; total prover time; and peak GPU memory.

Use these diagnoses without changing the relation or gates:

- high registration/D2H: keep correction formation resident;
- high dense-query time or Rayon scratch: replace the prover’s per-worker
  dense reduction with a bounded/device-side reduction;
- high H2D: construct query/bitmap directly in resident memory;
- high fold submit: optimize the fused CUDA kernel;
- high fold D2H/sync: keep coefficients resident until the close; and
- high PCS commit/open: optimize the existing batched resident PCS path,
  never add claims or proof bytes.
